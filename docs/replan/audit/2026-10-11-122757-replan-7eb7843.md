### Integration and feasibility

#### Integration feasibility review — Creator Rewards

**Verdict: ISSUES FOUND**

The design is directionally sound and unusually careful about not calling an Arcade checkout an order, but the core demo still lacks two executable contracts: how a customer co-pay reaches a Shopify test order, and exactly where a budget reservation is created before checkout. The repository is greenfield (only the spec plus an untracked `.gitignore`; no initial commit), so there is no existing application architecture to align with. The plan must therefore select and prove a minimal integration path before UI work.

#### Recommended minimal P0 route, auth and data handoff

1. Scaffold the current Shopify CLI React Router TypeScript app. Use managed installation/token exchange for the embedded merchant admin and retain an offline store session for server-side catalog reads and webhook reconciliation. P0 needs `read_products` and `read_orders`; do not request product/discount write scopes while co-pay collection is excluded.
2. Serve the creator landing page at a signed Shopify app-proxy route such as `/apps/creator-rewards/<campaign>`. Add a separate theme app block/embed for the cart offer and require the merchant to activate it. Arcade calls remain server-to-server with a bearer API key.
3. On the creator link, consent-aware storefront JavaScript stores the last-click campaign token. When the buyer selects a product, JavaScript sends that token, the Arcade product/selection and the current cart token/snapshot explicitly to a signed app-proxy/backend request; do not rely on proxy-forwarded cookies because Shopify strips them.
4. The server reloads authoritative campaign/product/economic inputs, calculates a **conditional** `D = 0` offer, and atomically inserts a reservation with a conditional campaign-budget update. It returns an opaque reservation ID bound to shop, campaign, quote version, Arcade product, expected qualifying Shopify lines and reserved amount. Store only that opaque ID in a private Shopify cart attribute (for example `__creator_reward_reservation`) and then continue to the normal Shopify test checkout. Any checkout without a valid reservation is an ordinary purchase with no reward.
5. On HMAC-verified `orders/paid`, load the authoritative Shopify order and reservation, recheck the actual qualifying lines/totals, then in one unique `(shop_id, order_id)` transaction consume the reservation and create a pending external reward claim plus pending internal commission. `orders/cancelled` and `refunds/create` reverse only unfulfilled claim/commission state. P0 never creates an Arcade checkout or marks manufacture paid.
6. If calculation yields `D > 0`, persist/display `AWAITING_COPAY`; do not collect, fulfill or count it as the integrated demo success. This retains the product vision while making the proven P0 boundary exact.

#### Critical issues

##### INT-1 — The co-pay is a calculation, not an implementable payment flow

- **Plan passage:** lines 43, 51, 60, 75, 96 and 112: the customer sees a final co-pay before payment, but “Doplatky v demu jsou testovací částky, ne skutečně inkasované peníze.”
- **Why:** These statements conflict. Arcade's documented checkout is a separate hosted payment page and creates an Arcade order only after that payment completes. Its request contains product lines and `dropShip`; it has no documented Shopify hand-off, merchant/customer split payment, or subsidy field. Shopify also cannot charge an arbitrary amount merely because the theme displays it: a Shopify checkout needs a priced product variant (or another supported line) and any subsidy must be represented by a real Shopify discount. Therefore a Shopify test order cannot currently prove that `D` was charged or matched to the selected Arcade product.
- **Concrete proposed change:** For the hackathon, choose one path explicitly:
  1. **Recommended narrow path:** make `D = 0` the only integrated checkout scenario. Reserve a fully sponsored reward as an external claim linked to the paid Shopify order; show `D > 0` only as a clearly labelled preview / “payment integration pending,” outside completion criteria.
  2. **Broader path, only after a spike:** publish/map one Arcade design to a real Shopify product variant priced at `G`; on reservation create a random, short-lived, `usageLimit: 1`, product-scoped fixed discount of `S`; add the variant plus opaque reservation ID to the cart and redirect to Shopify checkout. On `orders/paid`, verify the exact variant, discount, paid totals and reservation. This requires `write_products` and `write_discounts`, and still leaves Arcade fulfillment/payment manual. Do not claim this path until the product mapping and test order pass end to end.
- **Verified facts:** Arcade checkout is separate and payment creates its order; Shopify supports priced variants and fixed discount codes with expiry and usage limits.
- **Official sources:** [Arcade create checkout](https://docs.arcade.ai/api-reference/checkouts/create-a-checkout), [Shopify product variants](https://shopify.dev/docs/api/admin-graphql/latest/mutations/productVariantsBulkCreate), [Shopify fixed discount code](https://shopify.dev/docs/api/admin-graphql/latest/mutations/discountCodeBasicCreate), [discount input and usage limit](https://shopify.dev/docs/api/admin-graphql/latest/input-objects/DiscountCodeBasicInput).

##### INT-2 — A theme block cannot guarantee the promised pre-checkout reservation

- **Plan passage:** lines 43, 84, 104, 122 and 151: reserve atomically “před zahájením testovací platby,” while the storefront mechanism is only a theme app block and checkout itself is unchanged.
- **Why:** Theme app blocks cannot render on checkout pages, only work in compatible `@app` sections, and require merchant activation. Product/cart accelerated checkout buttons are separate routes and can bypass a custom cart CTA. Thus “theme block + no checkout modification” does not define a mandatory pre-payment interception point. The database transaction can be atomic while the customer path still bypasses it.
- **Concrete proposed change:** Define one controlled demo entry point: a custom **Reserve benefit and continue to checkout** action on the campaign landing/cart surface. The server must atomically lock the campaign row (or use a conditional update), create the reservation and signed/opaque reservation ID, then write that ID to the cart before redirecting to checkout. All other checkout paths remain available for ordinary purchases but are explicitly ineligible for the benefit. For the demo theme, remove/disable accelerated checkout on the eligible campaign surface and verify the app block/embed is activated. Add a two-browser concurrency test and a manual abandoned-reservation reset for MVP; automatic expiry remains a pilot prerequisite.
- **Verified facts:** App blocks cannot render on checkout; themes require supporting sections and merchant activation; accelerated checkout can exist on product pages, cart pages and cart drawers.
- **Official sources:** [theme app extension configuration](https://shopify.dev/docs/apps/build/online-store/theme-app-extensions/configuration), [accelerated checkout](https://shopify.dev/docs/storefronts/themes/pricing-payments/accelerated-checkout), [theme app extension activation/deep links](https://shopify.dev/docs/apps/build/online-store/theme-app-extensions/ux).

##### INT-3 — `G` cannot currently be proven before checkout from the documented Arcade API

- **Plan passage:** lines 25, 71, 75, 81, 108, 149 and 163: `G` includes product, shipping and fees; a free reward requires a complete current calculation; the pillow category and destination shipping must be confirmed.
- **Why:** `products/get` returns `unitPrice`, but the documented `checkouts/create` request has no shipping address or quote field. Shipping appears in `orders/get` only after an Arcade checkout has been paid and become an order. The public Arcade site shows pillow covers, but that does not prove the category is available to this API account, that the desired options have `canManufacture = true`, or that a chosen destination is supported. Without an authenticated read-only API preflight and a separately evidenced shipping amount, the app cannot establish the pre-checkout `G` needed for “free” or a truthful co-pay.
- **Concrete proposed change:** Add a blocking Gate 0 before implementation: obtain API-key access; call `categories/list`; select one returned print category; walk `categories/get` to a manufacturable selection; generate/retrieve one product; record product ID, currency and non-null `unitPrice`; and separately confirm destination eligibility plus shipping/tax source with Arcade. If no documented pre-payment shipping quote is available, use a dated merchant-entered shipping allowance labelled **modelled**, never **verified**. P0 may then demonstrate a **conditional/modelled `D = 0` sponsored claim**, but it must not call the landed cost verified or promise binding free fulfillment. A completed Arcade checkout may establish a reference cost, but would be a paid provider transaction and is outside this review's authority.
- **Verified facts:** category/option, manufacture and unit-price semantics are documented. **Unverified blocker:** current account category availability, API access, exact price, shipping destination and full landed cost.
- **Official sources:** [Arcade authentication](https://docs.arcade.ai/authentication), [list categories](https://docs.arcade.ai/api-reference/categories/list-categories), [retrieve category](https://docs.arcade.ai/api-reference/categories/retrieve-a-category), [retrieve product](https://docs.arcade.ai/api-reference/products/retrieve-a-product), [create checkout](https://docs.arcade.ai/api-reference/checkouts/create-a-checkout), [retrieve paid order](https://docs.arcade.ai/api-reference/orders/retrieve-an-order).

##### INT-4 — Attribution and payment reconciliation need one concrete, tamper-resistant join

- **Plan passage:** lines 44, 104, 106, 120, 122, 146, 150 and 152: carry the campaign ID into the order, verify it server-side, create exactly one claim after verified payment, and reverse it on cancellation.
- **Why:** Shopify cart attributes do carry into the resulting order, but storefront values are buyer-controlled and are not proof of campaign validity. The plan also does not name the reservation identifier, the paid/cancel/refund events, or what actual order fields must match the frozen quote. Deduplicating only by webhook delivery ID is insufficient because separate deliveries can represent the same business event.
- **Concrete proposed change:** Store a random reservation ID server-side, bound to shop, campaign, Arcade product/selection, frozen calculation version, expected qualifying Shopify lines, amount `S`, expiry/status and (if used) discount code/Shopify creator variant. Put only this opaque ID in a private cart/order attribute. On HMAC-verified `orders/paid`, perform one transaction keyed by `(shop_id, order_id)`: load the reservation, fetch/inspect the authoritative order, verify paid state, qualifying lines, actual discounts/totals and single reward, then consume the reservation and create claim/provision exactly once. Subscribe separately to `orders/cancelled` and `refunds/create`; make their transitions idempotent. Persist webhook delivery IDs for transport dedupe, but use the shop/order uniqueness constraint for business dedupe. Add a read-after-webhook reconciliation action for the demo.
- **Verified facts:** cart attributes carry into the resulting order; Shopify requires raw-body HMAC verification and warns that duplicate deliveries occur; webhook topics include `ORDERS_PAID`, `ORDERS_CANCELLED` and `REFUNDS_CREATE`.
- **Official sources:** [Storefront cart attributes](https://shopify.dev/docs/api/storefront/latest/objects/Attribute), [Ajax Cart API](https://shopify.dev/docs/api/ajax/reference/cart), [verify webhook deliveries](https://shopify.dev/docs/apps/build/webhooks/verify-deliveries), [webhook topics](https://shopify.dev/docs/api/admin-graphql/latest/enums/WebhookSubscriptionTopic).

### Economics data and security

#### Creator Rewards — economics, integrity, authorization, and abuse review

**Verdict: ISSUES FOUND**

The core per-order algebra is sound if every symbol is on the same tax/currency basis: `A = max(0, min(B, M-K))`, `S = min(G, A-C-F)`, and campaign spend `C+F+S` cannot exceed `A`. The plan also correctly separates Shopify order, reservation, customer claim, creator commission, and Arcade production states. The issues below are missing invariants and authorization details that can break those guarantees. No external claims were needed; this is a design and math review of the frozen plan.

#### Critical

##### ECON-1 — A released reservation can still become a paid order and overspend the campaign (demo blocker)

**Passage:** lines 43–45 reserve before payment and create the claim on verified payment; line 84 says verified cancellation releases the reservation and incomplete reservations are manually released; lines 86 and 122 describe later cancellation and state changes; lines 150–152 require duplicate, concurrency, and cancellation behavior.

**Why:** Idempotency for the same event does not handle different events delivered out of order. An operator can release an apparently abandoned reservation, another customer can consume the freed budget, and a late payment webhook can then create the first claim. `paid → cancelled`, `cancelled → paid`, repeated manual release, and payment racing manual release all need one authoritative transition rule. The current text therefore cannot guarantee the campaign cap under its own MVP lifecycle.

**Minimal fix:** Add an explicit transactional state machine and spend ledger. At minimum use `RESERVED`, `COMMITTED`, `RELEASED`, `CANCELLED`, and `MANUAL_REVIEW`; make transitions compare-and-set and append an immutable event/audit row. A verified payment may commit only an active reservation. If it arrives after release, atomically re-reserve the full merchant-funded spend or move the claim to `MANUAL_REVIEW` and block benefit/production. Cancellation releases only uncommitted/recoverable spend. Test duplicate and out-of-order payment/cancellation plus payment-versus-manual-release races. Manual expiry can remain acceptable for the demo if this late-payment rule exists.

##### ECON-2 — Quote, reservation, and order are not bound tightly enough to enforce the budget (demo blocker)

**Passage:** lines 42–44 recalculate the cart and reserve before payment; lines 82 and 85 bind a versioned offer to cart/variant/calculation; line 106 carries only the campaign identifier into the order; lines 120–122 require server calculations and per-order uniqueness; lines 147–151 claim the benefit never exceeds budget under concurrency.

**Why:** A campaign ID does not identify the exact quote or reservation. A replayed request, changed cart, second browser tab, or reused campaign link could create multiple holds or attach a paid order to a stale reservation. The plan also never states whether the reservation holds only `S` or the full campaign spend. Reserving only the product subsidy leaves creator commission and platform fee outside the total campaign cap.

**Minimal fix:** Generate one opaque `quote_id` and one `reservation_id`; persist both in trusted Shopify cart/order metadata and enforce unique constraints on `(shop_id, reservation_id)` and `(shop_id, order_id)`. The server-generated immutable quote must bind shop, campaign/terms version, eligible SKUs and quantities after discounts, currency/tax basis, destination country, reward product/variant, cost version, `C`, `F`, `G`, `S`, `D`, and validity window. Recompute from authoritative order data before committing. Atomically reserve `R = C + F + S`, with one active reservation per checkout/cart key and idempotent reserve calls.

##### ECON-3 — Real provider-cost and economic mutation endpoints lack a concrete principal and tenant boundary (public-demo blocker)

**Passage:** lines 37–40 cover merchant installation, campaign changes, invite, prompt/reference upload, and Arcade generation; lines 92–98 define merchant and creator screens; lines 104–108 require authorized Shopify installation and server-only Arcade calls; lines 120 and 155 say records are shop-bound and clients cannot overwrite economics.

**Why:** These are desired outcomes, not an enforceable authorization design. The plan does not say how merchant requests derive the canonical shop, how a creator authenticates and accepts an invite, who may call Arcade generation, or how object ownership is checked. A caller-supplied shop ID, creator ID, campaign ID, job ID, or merchant URL would allow cross-tenant reads/writes or spend through the platform's Arcade credential. Merely keeping the credential server-side does not prevent an unauthenticated server endpoint from spending it.

**Minimal fix:** Add a short authorization matrix for every state-changing route. Bind merchant sessions to the canonical shop returned by Shopify OAuth, validate OAuth state/nonce, and never derive access from a typed URL or request-body shop ID. Use expiring, single-use creator invites followed by an authenticated creator identity; check role plus `(shop_id, object_id)` ownership on every campaign, quote, dashboard, generation, job-status, and approval operation. Restrict Arcade generation to the invited creator/merchant, add per-shop/per-campaign job quotas and rate limits, and bind provider job/product IDs to that tenant. Treat the entered shop URL only as a validated Shopify-domain bootstrap value, never as an arbitrary fetch target. Before any public demo, verify webhook signatures against the raw request body, bind the event's shop/topic to the installed tenant, reject replay outside the idempotent event path, and treat campaign/quote IDs carried in order metadata as references to revalidate rather than trusted authorization.

#### Important

##### ECON-4 — A modeled co-pay is subtracted before there is proof it was collected (pilot gate; demo labeling fix)

**Passage:** lines 51 and 75 use customer co-pay `D` to finance production; lines 110–112 state that combined/split payment is unconfirmed and demo co-pays are test amounts, not collected money; line 122 creates a pending claim after Shopify payment.

**Why:** A paid Shopify merchandise order does not prove the separate creator-product co-pay was collected. If `D` is subtracted from campaign cost and the claim becomes fulfillable, the economic result assumes revenue the system explicitly says it did not receive.

**Minimal fix:** Make the narrow P0 paid-order path `D = 0` only. For `D > 0`, allow preview and at most a conditionally earned entitlement in `AWAITING_COPAY`; it must not be a ready-to-fulfill claim and must not trigger production. Before a pilot, require verified co-pay settlement (and refund/chargeback handling) before converting that entitlement into a fulfillable claim. The dashboard must not count modeled `D` as collected cash.

##### ECON-5 — `D` mixes an internal net contribution with the gross amount shown to the customer

**Passage:** line 60 requires one internal tax basis but shows the customer a final amount; lines 71 and 75 define `G`, `D = G-S`, and then say taxes/fees are recalculated.

**Why:** Subtracting a gross customer payment from a net production cost overstates funding whenever the co-pay carries tax or incremental payment/refund costs. “Recalculate afterward” is underspecified and can become circular. The illustrative formula is valid only if `D` is the net amount available to cover `G`.

**Minimal fix:** Split the variable into `D_net` (co-pay contribution after tax, incremental payment fees, and the stated refund reserve, on the same basis as `G`) and `D_gross` (customer-facing payable amount). Use `C + F + G - D_net <= A`, derive `D_gross` under explicit tax/rounding rules, then run the invariant again after rounding. Keep the existing example explicitly labeled tax-neutral/internal.

##### ECON-6 — Cancellation can release budget that has already become an incurred cost

**Passage:** line 84 broadly says verified cancellation releases the reservation; line 86 distinguishes unpaid production from already-paid production and sends the latter to manual handling; line 152 tests only an unfulfilled test cancellation.

**Why:** Once any provider fee, production charge, or non-refundable payment fee is incurred, releasing the full `C+F+S` makes available budget larger than the actual remaining funds. Partial refunds can also reduce `C` without making product cost recoverable.

**Minimal fix:** Track reserved, committed, incurred, refundable, and released amounts as ledger entries, not a single mutable balance. On cancellation/refund release only the recoverable component, preserve incurred cost, reverse only provisional commission, and send shipped/paid production plus partial-return cases to manual review. The MVP test may stay limited to an unfulfilled claim, but the UI and ledger must not present paid cost as restored budget.

##### ECON-7 — Creator consent is not attached to an immutable terms version

**Passage:** lines 7, 39–40, and 54 require creator agreement; line 85 versions the customer offer; line 120 lists stored entities but not acceptance evidence.

**Why:** A merchant could change commission, eligible products, attribution rules, or clawback terms after the creator agrees. A customer quote and a creator commission could then reference different economics, and there is no durable proof of which terms governed an order.

**Minimal fix:** Persist `terms_version`, exact commission rule, qualified SKUs, attribution window, refund/cancellation rules, creator acceptance timestamp/identity, and merchant approval. Changes create a new version; existing quotes/orders retain the accepted version, and creator-adverse changes require re-acceptance before new traffic qualifies.

##### ECON-8 — `G`, `C`, and `F` can double-count creator/platform compensation (pilot gate)

**Passage:** lines 54–56 prohibit an extra reward in the main mode and require complete standalone-sale economics; lines 69–71 define creator commission, platform fee, and full product cost; line 108 retrieves Arcade product price.

**Why:** The plan does not require checking whether the supplier price in `G` already includes a creator royalty, platform markup, or other revenue share. If it does, adding `C` or `F` may pay/count the same component twice. If it does not, standalone-sale margin may omit it.

**Minimal fix:** Store a line-item breakdown and provenance for `G` (manufacture, shipping, tax basis, non-refundable fees, co-pay handling reserve, embedded royalty/markup). Record explicitly whether Arcade price contains creator or platform compensation. Count every component exactly once in both modes; require this reconciliation before enabling real fulfillment or standalone sales. For the hackathon, unresolved components may remain labeled model assumptions.

##### ECON-9 — Public traffic can exhaust reservations even if it cannot steal funds

**Passage:** lines 41–43 expose a public campaign/cart flow; line 84 uses manual release for abandoned reservations; line 106 defines “last valid creator link” but not link validity; lines 120–122 make server-side reservations.

**Why:** A public caller can repeatedly create valid-looking carts/reservations and lock the whole campaign until an operator releases them. Guessable campaign identifiers can also forge attribution or enumerate active campaigns. This is a cost/availability failure specific to the design, amplified by manual-only cleanup.

**Minimal fix:** Define a valid creator link as an opaque, unguessable or signed campaign token scoped to the shop. Validate active campaign, allowed country/SKUs, and server-observed cart before quoting. Rate-limit quote/reserve by shop plus short-lived client/session key, make reserve idempotent per checkout/cart, cap active holds per key, and expose an audited operator release action. Automatic expiry can remain a pre-pilot item, but the demo must resist trivial repeated-hold exhaustion.

#### Minor

##### ECON-10 — Economic inputs need explicit bounds and currency invariants

**Passage:** lines 38–39 allow manually entered costs and limits; line 60 requires exact money; lines 66–71 define inputs.

**Why:** Negative values, mismatched currency, excessive percentages, unsupported currency precision, or integer overflow can invert the inequalities even with server-side calculations.

**Minimal fix:** State that all inputs are server-validated for currency match, non-negativity, configured maximums, valid commission range, and supported currency exponent; reject rather than clamp invalid inputs. Define the rounding direction used for `C`, `S`, and customer-facing `D_gross` conservatively for the merchant cap.

##### ECON-11 — Campaign availability should be a derived ledger value

**Passage:** lines 39, 84, 97, and 151 mention the total campaign limit, reservations, and concurrency but do not define the displayed remaining balance.

**Why:** A mutable “remaining budget” field can drift from reservations and committed spend after retries or manual handling.

**Minimal fix:** Define available campaign budget as `cap - active_reservations - committed_or_incurred_spend + explicit_recoveries`, computed transactionally from ledger rows (or a locked aggregate reconciled to them). Show reserved, committed/incurred, released, and available amounts separately in the merchant view.

#### Scope judgment

For a network-reachable/public three-minute hackathon demo, ECON-1 through ECON-3 are minimum blockers because the demo claims a hard budget cap before shopper commitment, exactly-once claims, tenant isolation, verified webhooks, and real Arcade integration. ECON-4 requires the P0 `D = 0` restriction plus a truthful distinction between a conditionally earned entitlement and a ready-to-fulfill claim. ECON-5 through ECON-11 can be implemented as explicit invariants, constrained demo behavior, and clearly marked pilot gates; the ledger must still distinguish reserved, committed/incurred, and released amounts after fulfillment. Real fulfillment, real co-pay, automatic release, payouts, and standalone sales should remain disabled until those gates are closed.


### Fresh product and UX

#### Fresh product / UX review — Creator Rewards

**Verdict: ISSUES FOUND**

Základní produktová myšlenka je čitelná a plán dobře odděluje skutečná data, testovací Shopify objednávku a neprovedené plnění. To je silný základ pro věrohodné demo. V současné podobě je však hackathonový rozsah příliš široký a zákaznická cesta nemá pravdivý, jednoznačný konec: UI ukazuje „celkovou cenu“ a doplatek za creatorův produkt, ale demo tento doplatek neinkasuje ani produkt neobjedná. To je nutné opravit před realizací. Výhra v hackathonu je designová ambice, ne garantovaný výsledek; závisí hlavně na kvalitě provedení, volbě žádoucího produktu a jasnosti tříminutového příběhu.

#### Critical

##### UX-1 — Hackathonové P0 je přetížené třemi produkty najednou

**Pasáž:** ř. 21–23 („jeden obchod, creator, kampaň…“), ř. 35–45 (devítikroková cesta tří rolí), ř. 88–98 (sedm obrazovek), ř. 140–155 (12 kritérií včetně souběhu a storna) a ř. 5, 47–56, 161 (samostatný prodej jako druhý režim).

**Proč:** Executor má současně stavět merchant onboarding, creator workflow, customer storefront, živé generování, ekonomický engine, rezervace, webhookové stavy, dva dashboardy, souběh a storno. To může vyprodukovat mnoho polohotových obrazovek a žádnou přesvědčivou vertikální cestu. Samostatný prodej je v úvodu a obchodním modelu natolik viditelný, že působí jako součást slibu, přestože je odložený. Pro porotu i implementátora není jasné, co se má obětovat jako první.

**Minimální změna:** Přidat před „Rozsah hackathonového MVP“ explicitní pořadí:

1. **P0 demo-blocking:** přednastavený jeden obchod, creator a kampaň; jeden skutečný Arcade produkt; creator landing; dva košíky; jedna Shopify testovací objednávka; právě jeden evidovaný nárok; merchant výsledek s pravdivými stavy.
2. **P1, jen pokud P0 funguje:** editace kampaně, creatorova tvorba/acceptance UI a creator dashboard.
3. **Pilot-hardening:** obecný onboarding, uživatelské role, storno UI a demonstrační test souběhu; implementovat jen to, co je nutné pro konkrétní tvrzení v demu.

Samostatný prodej odstranit z úvodu a tabulky MVP a ponechat pouze v „Co patří do další fáze“. Generování může proběhnout před demem ze skutečného jobu; během tří minut se pouze prokáže původ produktu a případně spustí nový job bez čekání.

##### UX-2 — Zákazník nepozná, co po testovací objednávce skutečně získal

**Pasáž:** ř. 43–45 („před potvrzením… celkovou cenu, příspěvek a doplatek“; nárok po testovací objednávce), ř. 110–112 (Arcade checkout je oddělený; doplatky nejsou inkasované), ř. 128–138 (demo končí nárokem a čekající provizí).

**Proč:** Hlavní customer promise zní jako získání produktu, ale skutečný konec dema je jen testovací Shopify objednávka a záznam nároku. Pokud CTA nebo potvrzení vypadá jako objednávka creatorova produktu, publikum i zákazník mohou oprávněně chápat doplatek, výrobu a doručení jako dokončené. To rozbíjí důvěru a zároveň zamlžuje, co bylo technicky dosaženo.

**Minimální změna:** Doplnit přesný demo copy contract a acceptance criterion:

- před platbou: „Shopify testovací objednávka: X; modelovaný příspěvek: Y; neinkasovaný doplatek creatorova produktu: Z“;
- CTA: „Vytvořit testovací objednávku a rezervovat nárok“;
- po objednávce: „Nárok je evidovaný a čeká na ruční vyřízení. Creatorův produkt zatím nebyl zaplacen, objednán ani odeslán.“;
- merchant stav: `claim pending manual fulfillment`, nikdy `reward ordered`.

Do kritérií dokončení přidat samostatný průchod potvrzovací obrazovkou a ověřit, že žádný zákaznický text netvrdí nákup, výrobu nebo doručení creatorova produktu.

#### Important

##### UX-3 — Chybí jednotný stavový model nabídky pro zákazníka

**Pasáž:** ř. 41–43 (kolekce, měnící se košík a nabídka), ř. 81–85 (neznámé náklady, přepočet a rezervace), ř. 96 a 100 (cart offer a mobilní použití).

**Proč:** Plán říká, co se má počítat, ale neříká, co zákazník uvidí v každém výsledku. Benefit nemusí růst s hodnotou košíku, může zmizet po změně varianty nebo země a může selhat rezervace. Bez pojmenovaných stavů bude UI působit nahodile nebo jako bait-and-switch. To je největší překážka srozumitelné customer journey.

**Minimální změna:** Definovat pro landing/cart jednu komponentu s pěti stavy a jednou hlavní akcí: `ověřujeme cenu/dopravu`, `nezpůsobilé`, `příspěvek + doplatek`, `zdarma`, `rozpočet se nepodařilo rezervovat`. U každého uvést krátký důvod a bezpečný další krok („pokračovat bez reward“, „změnit košík“, „zkusit jiný návrh“). Zemi ověřit před prvním slovem „zdarma“. Nezobrazovat obecný progress bar k vyššímu benefitu, protože plán sám správně říká, že vyšší košík nemusí znamenat vyšší příspěvek.

Ve všech stavech sjednotit copy: `příspěvek na creatorův produkt` pro customer offer, `nárok` pro post-purchase record a `provize creatora` pro creator earnings. Slovo `zdarma` použít jen při D = 0; `dárek` nepoužívat pro produkt s doplatkem.

##### UX-4 — Creator nemá skutečný okamžik informovaného souhlasu

**Pasáž:** ř. 7 („Creator s rozdělením odměny předem souhlasí“), ř. 32, 39–40 (potřeby a workflow creatora), ř. 54 (možné snížení běžné provize), ř. 98 (creator vidí pouze stavy provizí).

**Proč:** Creator investuje motiv, jméno a distribuci, ale plán neukazuje obrazovku ani kritérium, kde před sdílením rozumí své odměně. Zvlášť citlivé je, že může dostávat jen affiliate provizi a případně nižší než obvykle, bez další odměny za produkt. Evidence výdělku po nákupu tento souhlas nenahrazuje.

**Minimální změna:** Přidat před publikací kolekce jedno shrnutí podmínek, i kdyby v hackathonu šlo jen o přednastavený potvrzený záznam: sazba a základ provize, žádná další product royalty v hlavním režimu, sedmidenní atribuční okno, kvalifikované položky, konec/limit kampaně, kdy je provize pending/confirmed/cancelled a co se stane při vyčerpání rozpočtu. Zahrnout checkbox/čas souhlasu a náhled přesně té nabídky, kterou uvidí fanoušek.

##### UX-5 — Povlak na polštář je zatím neověřená designová hypotéza, ne demo asset

**Pasáž:** ř. 25 („kandidátem je outdoorový povlak… vhodnost potvrďte“), ř. 131 (porotě se ukazuje creatorův skutečný produkt).

**Proč:** Technická dostupnost kategorie neznamená, že produkt bude pro fanouška žádoucí, vizuálně působivý nebo přirozený pro konkrétní partnerství. Slabý produkt znehodnotí „wow“ moment i při správné integraci. Plán to částečně přiznává slovem kandidát, ale chybí rozhodovací brána před implementací customer journey.

**Minimální změna:** Přidat krátký Stage 0 gate: z aktuálně dostupných kategorií vybrat jeden produkt až po kontrole (a) creator/Jackery fit, (b) vizuálního výsledku, (c) srozumitelné varianty a toho, co balení obsahuje, (d) ověřitelné ceny a dopravy do demo země. Pokud pillowcase gate nesplní, změnit produkt bez změny obchodní hypotézy. V dokumentu i pitchi jej do té doby označovat jako kandidáta.

##### UX-6 — Tříminutové demo začíná konfigurací místo zákaznické hodnoty

**Pasáž:** ř. 128–136 (merchant → creator → customer → ekonomika → claim), ř. 138 (rozlišení typů dat).

**Proč:** V prvních desítkách sekund porota uvidí administraci a rozpočet, ale hlavní „aha“ je exkluzivní creator produkt financovaný ekonomikou košíku. Tři role za tři minuty navíc snadno vypadají jako tři nesouvisející prototypy. Plán nemá časový budget ani explicitní vizuální důkaz, která data jsou živá, testovací a modelová.

**Minimální změna:** Přepsat demo pořadí a čas:

1. 0:00–0:30 — fanoušek otevře creator link a vybere jeden produkt;
2. 0:30–1:15 — dva košíky ukážou srozumitelnou změnu příspěvku/doplatku;
3. 1:15–2:00 — testovací Shopify objednávka vytvoří jeden pending claim;
4. 2:00–2:35 — merchant vidí, proč objednávka zůstala zisková; creator vidí pending provizi;
5. 2:35–3:00 — ukázat skutečné Arcade product ID/job/cenu a jasně vyjmenovat neprovedené fulfillment kroky.

Merchant konfiguraci přednastavit. Na všech demo obrazovkách používat stejné čtyři badge: `LIVE ARCADE`, `SHOPIFY TEST`, `MODELOVÁ EKONOMIKA`, `NEPROVEDENO`.

##### UX-7 — Technická definition of done není zároveň užitečný business handoff

**Pasáž:** ř. 140–157 (technická kritéria a předávané artefakty), ř. 165–171 (budoucí pilot a metriky).

**Proč:** Projekt může splnit technická kritéria, ale existující ILICO/Jackery partnerství stále nebude vědět, co přesně zkusit jako další placený experiment. Naopak demo nesmí budoucí metriky vydávat za výsledek. Chybí artefakt, který oddělí ověřené skutečnosti od designových a obchodních hypotéz.

**Minimální změna:** K hackathonovému handoffu přidat jednostránkový „pilot decision sheet“ se čtyřmi sloupci: `ověřeno živě`, `ověřeno jen testovací objednávkou`, `modelová hypotéza`, `blokuje reálný pilot`. Uvést jednoho zamýšleného typu creatora, jednu zemi, jeden produkt, baseline affiliate nabídku a přesný první experiment bez tvrzení o očekávaném liftu. Kritériem hackathonu je připravenost tohoto experimentu, nikoli naměřený obchodní úspěch.

#### Minor

Žádné další drobné nálezy nejsou pro hackathonový řez rozhodující.

#### Co bude executor chtít vědět předem

- Kterých pět kroků je P0 a co se při nedostatku času bez diskuse zahodí.
- Jak přesně vypadá poslední zákaznická obrazovka, když Arcade objednávka a doplatek nejsou provedené.
- Který produkt, země a creator jsou pro demo zvolené až po Stage 0 gate.
- Jaká konkrétní creatorova dohoda je v demu modelovaná a zda je skutečně odsouhlasená, nebo pouze ukázková.
- Které badge musí být na každé obrazovce, aby porota okamžitě odlišila live, test a model.

#### Nejjednodušší smysluplný řez

Jedna přednastavená kampaň, jeden skutečný Arcade produkt, jedna creator landing page, jedna cart-offer komponenta, jedna Shopify testovací objednávka, jedna merchant result page a statický creator earnings panel. To stačí ukázat zákaznickou hodnotu, ekonomickou logiku i existující partnerství. Obecný onboarding, plná creator samoobsluha, standalone sale a pilotní provozní automatizace mohou následovat po hackathonu.
